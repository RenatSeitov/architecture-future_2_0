

# Task 1 — Архитектура системы «Будущее 2.0» через год

## 🎯 Цель

Разработать архитектуру системы на год вперёд, учитывая стратегические планы компании:

- Масштабирование бизнеса в области медицины, финансов и новых направлений (фармацевтика, электроника).
- Снижение time-to-market для отчётности и аналитики.
- Упрощение интеграции новых бизнесов и сервисов.
- Разделение ответственности между доменами.

---

## 🧱 Ключевые проблемные места

**1. Перегруженный DWH**
  
Историческое хранилище данных (Microsoft SQL Server 2008) содержит всю бизнес-логику и данные. Это монолит, из-за которого даже простые отчёты строятся по несколько часов. Сложно масштабировать, невозможно гибко развивать отдельные направления.

**2. Отсутствие витрины данных и self-service-аналитики**
  
Все обращения за данными проходят через IT, бизнес не может самостоятельно собирать и настраивать отчёты. Это снижает оперативность принятия решений и тормозит развитие.

**3. Нет разделения данных по доменам**

Финансы, медицина, управление клиниками, ИИ — всё смешано в одной базе. Любые изменения могут повлиять на все направления, что создаёт риски и замедляет внедрение новых функций.

**4. Устаревшая интеграционная шина**

Используется Apache Camel, поддержка требует много ресурсов, а подключение новых систем требует значительных усилий.

**5. Использование устаревших технологий**

Power Builder и SQL Server 2008 — морально и технически устаревшие инструменты, их сложно поддерживать, дорого масштабировать и невозможно развивать.

**6. Отсутствие централизованной системы контроля доступа**

Данные передаются между компонентами без строгой и гибкой модели разграничения прав. Это создаёт потенциальные риски безопасности.

**7. Дублирование бизнес-логики в BI и ML**

Разные команды воссоздают бизнес-логику при формировании отчётов и обучении моделей. Это приводит к несовпадению данных и потере доверия к аналитике.

**8. Трудности интеграции новых бизнесов**

Каждое новое направление (финтех, фармацевтика и т. д.) требует дописывания логики в старом DWH, что дорого, долго и рискованно.

---

## ✅ Приоритизация проблем (по методу MoSCoW)

**Must (обязательно)**

- Внедрение Data Lake и разделение данных по доменам.
- Создание портала витрины данных с возможностью self-service.
- Вынос бизнес-логики из DWH в отдельные сервисы.
- Обеспечение производительности и масштабируемости аналитики.

**Should (желательно)**

- Замена интеграционной шины на Kafka или другое современное решение.
- Внедрение гибкой модели доступа и безопасности.
- Стандартизация API и потоков данных между бизнесами.

**Could (можно сделать при наличии ресурсов)**

- Постепенный отказ от Power Builder.
- Расширение возможностей BI-инструментов.

**Won’t (не делаем в этом году)**

- Полный отказ от DWH — только постепенный вывод функциональности.

---

## 🔚 Вывод

Для того чтобы компания «Будущее 2.0» могла успешно масштабироваться и интегрировать новые бизнесы, необходима трансформация архитектуры с фокусом на:

- Разделение по доменам.
- Введение гибкой и масштабируемой витрины данных.
- Уход от монолита и устаревших технологий.
- Оптимизация процессов интеграции и аналитики.

Это позволит обеспечить устойчивость и гибкость архитектуры, сократить время вывода новых решений и повысить доверие к аналитике.
