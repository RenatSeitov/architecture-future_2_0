## 🛣️ Роадмап технологических изменений

> Отрисуй в draw.io, Miro или другой удобной платформе. Здесь — описание для вставки в README.

### 📅 Этап 1: Подготовка (1–3 месяца)
- **Результаты**: Определены границы доменов, выбран стек для Data Lake, начат PoC Kafka
- **Команды**: Архитекторы, data-инженеры
- **Ресурсы**: Временные sandbox-окружения, поддержка DevOps

### 📅 Этап 2: Запуск базовой архитектуры (3–6 месяцев)
- **Результаты**: Работает Kafka, отдельные домены выделены (финтех, BI), self-service BI MVP
- **Команды**: Финтех, BI, DevOps
- **Ресурсы**: Облачные ресурсы, временные миграционные скрипты

### 📅 Этап 3: Переход от DWH к доменам (6–9 месяцев)
- **Результаты**: Новые данные идут напрямую в Data Lake, часть логики выведена из DWH
- **Команды**: DWH, аналитики, архитекторы
- **Ресурсы**: Специалисты по SQL и BI, временная поддержка легаси

### 📅 Этап 4: Подключение новых бизнесов (9–12 месяцев)
- **Результаты**: Интеграция партнёрского домена (фарма, электроника), DWH в read-only
- **Команды**: Интеграционная, партнёрская, архитекторы
- **Ресурсы**: REST/gRPC-шлюзы, продакшн Kafka, документация API

## 🧠 Обоснование этапов

### Этап 1: Подготовка
Без ясного понимания границ и технологии (PoC) любые последующие шаги будут неустойчивыми. Здесь формируется общий технический план и архитектурная целевая модель.

### Этап 2: Запуск базовой архитектуры
Нужен рабочий фундамент, на котором можно будет строить остальные домены. Kafka как основа для событийной шины, Data Lake как новое хранилище данных.

### Этап 3: Переход от DWH
Переход к распределённой логике критичен: он позволяет обойти узкое место в виде монолита. Вывод логики в сервисы увеличит гибкость и ускорит Time-to-Market.

### Этап 4: Интеграция новых бизнесов
Финальная проверка архитектуры в бою: подключение внешних компаний. Без этого компания не сможет масштабироваться и расти.
